# Требования к оборудованию для промышленной эксплуатации

Документ отделяет **измеренное** от **рекомендуемого**. Измерения сделаны один раз на одной машине (раздел 1). Нагрузочного тестирования, замеров на парке из сотен активов, тестов отказоустойчивости и Windows/macOS/arm64 не проводилось; рекомендации для них — инженерная оценка с запасом, а не результат испытаний. Перед промышленным запуском их нужно подтвердить пилотом на вашем железе и вашем числе активов.

## 1. Что измерено

Стенд: ноутбук Intel Core i5-1235U (12 потоков), 23 ГБ ОЗУ, NVMe, Linux x86-64, Python 3.12, CPU без GPU.

| Показатель | Значение | Как получено |
|---|---|---|
| Образ контейнера | около 2 ГБ на диске (434 МБ сжатого содержимого) | `docker images` |
| Память процесса API после запуска и 5 запросов | около 373 МБ RSS | `/proc/<pid>/status` |
| Ответ `/api/battery/example` | 1–5 мс на локальном соединении | `curl`, 6 запросов |
| Прогноз всеми моделями по одному окну | около 8 мс | `method_experiment`, поле `latency` |
| Размер обученных моделей | GB ≈ 0,2 МБ, GPR ≈ 5 МБ, пакет весов детектора и RUL около 3 МБ | файлы в `artifacts/` и `metrics.json` |
| Полный эксперимент сравнения методов (77 ячеек HUST, 10 процессов) | 29 секунд | `method_experiment --workers 10` |
| Локальный каталог данных `artifacts/battery-local` | 5,8 ГБ (исходники NASA, CALB, HUST и кэши) | `du` |

GPU не используется ни в обучении, ни в выводе: образ собран на CPU-версии PyTorch.

## 2. Рекомендации по ролям

Числа в таблицах — **рекомендации**, кроме тех, что совпадают с измерениями выше.

### 2.1. Только вывод (дашборд и API), до нескольких десятков активов

| Ресурс | Минимум | Рекомендуется |
|---|---|---|
| CPU | 2 ядра x86-64 | 4 ядра |
| ОЗУ | 1 ГБ | 2 ГБ (измерено 0,4 ГБ у процесса, остальное — запас на ОС и контейнерный движок) |
| Диск | 5 ГБ (образ 2 ГБ, том весов, журналы) | 20 ГБ SSD |
| Сеть | 100 Мбит/с | 1 Гбит/с, локальная сеть предприятия |
| GPU | не нужен | не нужен |

Один экземпляр сервера одновременно выполняет приём и вывод. Запас по производительности для сотен активов и тысяч одновременных клиентов **не измерялся**.

### 2.2. Переобучение моделей (`scripts/train_all.sh`) и эксперименты

| Ресурс | Минимум | Рекомендуется |
|---|---|---|
| CPU | 4 ядра | 8–12 ядер |
| ОЗУ | 8 ГБ | 16 ГБ |
| Диск | 20 ГБ свободно | 50 ГБ SSD, если нужны все открытые наборы (5,8 ГБ) и несколько пакетов весов |

Если запускать эксперименты на нескольких процессах, задайте `OMP_NUM_THREADS=1`, иначе потоки BLAS перегружают машину: так первый прогон сравнения методов занял 50 минут вместо 29 секунд. Бэктест на 108 ячейках занимает около 35 минут процессорного времени; здесь он после исправления шага не пересчитывался.

### 2.3. Сборка из исходников

Компилятор C++20 (GCC или Clang), CMake, Ninja, Python 3.12, 4 ГБ ОЗУ и около 10 ГБ диска на `.venv` (1,5 ГБ у нас) и сборку. В образе всё это делает многоэтапная сборка; на машине эксплуатации компилятор не нужен.

## 3. Программная среда

- Docker Engine или Docker Desktop с Compose v2. Проверено на Linux x86-64 (CI и локально).
- arm64: тот же Dockerfile собирается, но здесь не проверялся.
- Windows и macOS (Docker Desktop): не проверялись.
- Контейнер работает без root (uid 10001), с `read_only`, `cap_drop: ALL`, `no-new-privileges`. Веса и данные хранятся в именованном томе `argus-data`.
- Порт 8000. По умолчанию привязан к `127.0.0.1`.

## 4. Условия для промышленной среды

Прототип **не готов** к прямой публикации в сеть. Ниже — что нужно сделать вне ПО.

1. **Аутентификации в API нет.** Не открывайте порт наружу. Поставьте перед ним обратный прокси с TLS и аутентификацией (или закройте сетевой политикой), прежде чем менять адрес привязки в `docker-compose.yml`.
2. **Источник данных.** Дашборд показывает синтетический генератор и открытые лабораторные данные. Адаптеров к реальной телеметрии (OCPP, Modbus, CAN, вендорские API) нет, как и измерений ложных тревог на реальных активах.
3. **Хранение и копии.** Веса и результаты лежат в томе `argus-data`: настройте регулярное копирование тома и хранение предыдущих пакетов весов (новые пакеты активируются только после проверки, старые сохраняются).
4. **Один экземпляр.** Встроенной репликации, балансировки и отказоустойчивости нет. Для требований по доступности предусмотрите автоматический перезапуск (в Compose включён `restart: unless-stopped`) и внешний мониторинг `/api/health`.
5. **Время и журналы.** Синхронизируйте часы хоста (NTP); подключите сбор журналов контейнера и ротацию.
6. **Граница применимости.** Метрики получены на ячейках LFP в лаборатории; перенос на пакеты EV, БПЛА, самокаты и пауэрбанки не проверялся. Для оборудования реальных заказчиков требуется собственная валидация.

## 5. Как проверить на своём железе

```bash
docker compose up -d --build
docker compose exec argus bash scripts/train_all.sh
docker compose restart argus
bash scripts/docker_smoke.sh
docker stats --no-stream
```

Запишите потребление памяти и процессора при вашем числе активов и сравните с таблицей 2.1 до расширения парка.
