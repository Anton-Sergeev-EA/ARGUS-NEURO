# План: адаптер OCPP и эмулятор станции для CI (черновик 30.10.2026)

**Статус (30.10.2026): реализовано на эмуляторе, см. [OCPP_COLLECTOR.ru.md](OCPP_COLLECTOR.ru.md).** Реальной станцией не проверено; пакеты работ 1–8 выполнены, вопросы раздела 5 решены по умолчанию (`ocpp` необязательная зависимость, токен на входе, `idTag` не хранится). Исходный текст плана ниже. Выбор «комплект А + комплект В» из [FIELD_KIT.ru.md](FIELD_KIT.ru.md).

## 1. Что показало чтение кода (до проектирования)

| Находка | Где | Следствие |
|---|---|---|
| У сервера **нет входа для внешней телеметрии оборудования**: `/ws/telemetry` только рассылает снимки симулятора `LiveFleet`, `/api/fleet` отдаёт тот же снимок | `python/argus/api/server.py` | Нужна новая точка приёма или прямой вызов движка; без неё адаптеру некуда писать |
| Движок принимает отсчёт только с **шестью каналами** и шагом **5 с ±10 %**, иначе сбрасывает буфер (`missing_sensors`, `sampling_gap`) | `HealthInferenceEngine.push_sample` | Данные OCPP нужно привести к сетке 5 с и к шести каналам |
| Модели обучены на **синтетике** | README, `docs/USE_CASES.md` | Реальные данные станций для моделей вне распределения: диагностика станции не будет проверена, пока нет размеченных отказов |
| Батарейная часть принимает ёмкость в А·ч по циклам при одинаковых условиях | `BatteryRequest` | OCPP такой величины не даёт; адаптер для батарей не строится (комплект А уже работает через CSV) |

## 2. Что OCPP может и не может дать

Проверено по перечислению `Measurand` в пакете `ocpp` 2.1.0 (профиль 1.6).

| Канал ARGUS | Измеряемая величина OCPP | Комментарий |
|---|---|---|
| `voltage_v` | `Voltage` | Если станция сообщает |
| `current_a` | `Current.Import` | |
| `temperature_c` | `Temperature` (место: разъём, корпус) | Поддержка зависит от станции |
| `frequency_hz` | `Frequency` | Поддержка зависит от станции |
| `load_factor` | `Power.Active.Import` / `Power.Offered` | Считается как отношение |
| `vibration_g` | **нет** (есть только `RPM`) | Нужен отдельный датчик (ADXL355, см. FIELD_KIT) и свой канал данных |

Отдельные ограничения:
- Интервал `MeterValueSampleInterval` настраивается, но минимальное значение и нагрузка на станцию зависят от модели; **проверить на реальной станции**. Типовые значения заметно больше 5 с.
- Станции с OCPP 1.6 не работают с 2.0.1; начинаем с 1.6.
- `idTag` (карта RFID) и идентификаторы транзакций могут быть персональными данными: хранить не нужно, нужны только анонимный идентификатор станции и времена.

**Вывод:** адаптер OCPP даёт сбор и хранение телеметрии станций и основу для будущей разметки. Подавать её в нынешние модели оборудования в режиме «как есть» нельзя: нет вибрации и другая частота дискретизации. Заявлять диагностику реальных станций на этом нельзя.

## 3. Архитектура

```
станция (OCPP 1.6J, WebSocket) ──► CSMS (адаптер) ──► хранилище SQLite (сырые MeterValues)
                                         │
                                         ├─► ресемплер на сетку 5 с ──► ingest-вход ARGUS ──► движок
                                         └─► журнал качества данных (пропуски, дубли, нет каналов)
эмулятор станции ──► тот же CSMS (для CI и демонстраций)
```

Решения:
- **Библиотека:** пакет `ocpp` (PyPI, лицензия MIT, по метаданным Python ≥ 3.11, зависимость `jsonschema`). Проект заявляет Python 3.10+, CI на 3.12: адаптер должен быть необязательным модулем, а зависимость — в отдельном extra.
- **Хранилище:** SQLite, только параметризованные запросы; сырые сообщения сохраняются без изменений, производные таблицы строятся из них.
- **Ресемплер:** удержание последнего значения на сетке 5 с с пометкой «устарело», если значению больше, чем одно окно; интерполяции нет, чтобы не создавать данных, которых станция не присылала. Отсутствующий канал даёт `missing_sensors`, как и сейчас.
- **Вход ARGUS:** новый маршрут приёма с обязательным токеном (сегодня у API нет аутентификации, открывать приём без неё нельзя) и лимитом скорости, как у батарейных маршрутов (`limit_requests`).
- **Безопасность канала OCPP:** профили безопасности OCPP (TLS и аутентификация станции) включаются в план как условие выхода за пределы localhost.

## 4. Пакеты работ и критерии приёмки

| № | Работа | Критерий приёмки (до начала) |
|---|---|---|
| 1 | Таблица отображения измеряемых величин OCPP в каналы ARGUS, единицы, места измерения | Тесты на каждую величину и единицу; отсутствующие величины не подменяются |
| 2 | CSMS: `BootNotification`, `Heartbeat`, `StatusNotification`, `StartTransaction`, `StopTransaction`, `MeterValues` | Ответы проходят проверку схем библиотеки; неизвестное действие отвечает ошибкой, не падает |
| 3 | Хранилище SQLite и политика хранения | Повторное сообщение не дублирует запись; `idTag` не сохраняется |
| 4 | Ресемплер на сетку 5 с | Тесты: пропуск, дубль, обратное время, уход часов; результат совпадает с эталоном по фиксированным сообщениям |
| 5 | Вход ARGUS с токеном и лимитом | Без токена 401; с токеном данные доходят до `push_sample`; тесты API |
| 6 | Эмулятор станции (клиент `ocpp`) со сценариями: здоровая, перегрев, потеря связи, нет части каналов, дубликаты, дрейф часов; детерминированный по зерну | Сценарии воспроизводимы; один и тот же результат на двух запусках |
| 7 | Задача CI: CSMS и эмулятор в одном прогоне, проверка записи и флагов качества | Работает без оборудования, укладывается в минуты; не поднимает порог покрытия выше достижимого |
| 8 | Документация: что адаптер делает, чего не делает, сводка ограничений из раздела 2 | `check_docs` проходит; формулировок о «диагностике реальных станций» нет |

Что остаётся вне плана: адаптер к конкретной модели станции (отличается набором величин и интервалом), датчик вибрации, анализатор сети по Modbus, размеченные отказы, валидация моделей на реальных данных.
